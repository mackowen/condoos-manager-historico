## 4. Auditoria do grafo e causa herdada

O lockfile era formato 9.0. Versões já fixadas relevantes:

| Pacote | Versão | Binário Android ARM64 disponível |
|---|---:|---|
| esbuild | 0.27.3 | `@esbuild/android-arm64` |
| Rollup | 4.59.0 | `@rollup/rollup-android-arm64` |
| Lightning CSS | 1.31.1 | `lightningcss-android-arm64` |
| Tailwind Oxide | 4.2.1 | `@tailwindcss/oxide-android-arm64` |

Os quatro pacotes Android estavam excluídos por `overrides` em `pnpm-workspace.yaml`. O comentário herdado afirmava que o conjunto atendia Linux x64/Replit. O lockfile registrava apenas os candidatos linux-x64 desses motores nativos. As versões fixadas já publicavam binários Android ARM64; não foi necessário upgrade.

Os candidatos Linux ARM64 têm alvos Linux (glibc ou musl em vários casos) e não são intercambiáveis com Android/Bionic. O próprio pnpm selecionou os pacotes Android ao rodar no host. Não havia `supportedArchitectures` nem `ignoredOptionalDependencies` no workspace. A regra `minimumReleaseAge: 1440`, a exceção de idade para `@replit/*`/`stripe-replit-sync`, o catálogo e plugins `@replit/*`, e os demais overrides foram mantidos. `onlyBuiltDependencies` autoriza scripts de `@swc/core`, esbuild, msw e unrs-resolver; nenhum script de banco/seed é aprovado por essa lista.

Arquivos do principal incluídos no commit:

- `pnpm-workspace.yaml`: permite a resolução dos quatro optional dependencies Android já suportados pelas versões travadas.

A tentativa final com pnpm 10 preservou a política `onlyBuiltDependencies` existente.

## 7. Gate A — Instalação

**PASS.** `pnpm install` direto, com pnpm 10.30.1, concluiu: `Already up to date`, `Done in 6s`. A primeira instalação que preencheu o store concluiu após a correção e baixou 508 pacotes, selecionando:

- `@esbuild/android-arm64@0.27.3`;
- `@rollup/rollup-android-arm64@4.59.0`;
- `lightningcss-android-arm64@1.31.1`;
- `@tailwindcss/oxide-android-arm64@4.2.1`.

O `postinstall` do esbuild concluiu. A instalação final direta não alterou lockfiles além das entradas previstas. `node_modules` está ignorado pelo Git.

## 8. Gate B — Typecheck

**PASS.** `pnpm run typecheck` executou `tsc --build` para libs e os scripts oficiais de typecheck de `condo-saas`, `mockup-sandbox`, `api-server` e `scripts`. Todos concluíram sem erro. Não foram encontrados bloqueadores de portabilidade, erros preexistentes de código, codegen ausente ou erros de configuração de typecheck.

## 9. Gate C — Build

**PASS.** O primeiro `pnpm run build` parou antes de compilar porque as configs Vite exigem `PORT` e `BASE_PATH` até mesmo para build. Repetido como `PORT=4173 BASE_PATH=/ pnpm run build`, concluiu:

- `mockup-sandbox`: Vite 7.3.2;
- API server: esbuild 0.27.3, com saída `dist/index.mjs` e workers;
- `condo-saas`: Vite 7.3.2/Rollup 4.59.0, Tailwind 4.2.1 e Oxide Android ARM64.

Assim, esbuild, Rollup, Vite, Lightning CSS e Tailwind/Oxide foram exercitados no build Android. Avisos sem bloqueio: Node emite `DEP0205` para `module.register()`, sourcemaps de alguns componentes não localizaram posições originais, e o bundle principal excede 500 kB após minificação. Artefatos `dist` são ignorados por `.gitignore`. O build da API removeu e recriou `artifacts/api-server/dist`, pasta de artefatos já gerados e ignorados.

## 10. Gate D — Startup técnico

- **Frontend: PASS.** `condo-saas` subiu no Vite em `http://localhost:4179/` com `PORT=4179` e `BASE_PATH=/`; smoke HTTP local retornou `200 text/html` (1750 bytes). Processo encerrado com SIGINT e não havia processo Vite restante.
- **API: ADIADO PARA POSTGRESQL.** `lib/db/src/index.ts` lança erro na importação se `DATABASE_URL` não estiver definido e cria `pg.Pool` assim que existe URL. Não foi inventada URL nem iniciada conexão. API não foi iniciada.
