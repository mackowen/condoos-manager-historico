## Auditoria e implementação

- A API exporta o Express app sem iniciar listener e usa Drizzle/PostgreSQL com migrations versionadas. O workspace já tinha `node:test` no Node e `tsx` no pacote `@workspace/scripts`; não foi necessário adicionar framework ou dependência.
- A suíte sobe o app em porta loopback efêmera dentro do processo. O runner valida primeiro o usuário, o banco e o host local usando `psql` em modo não interativo. Somente depois executa `drizzle-kit migrate` e os testes. O banco nunca é removido ou recriado.
- O guard permanente aceita somente `condoos_app` em `condoos_e2e` no PostgreSQL local. Ele rejeita `condoos`, `rotamoto`, `rotamoto_e2e` e qualquer nome não autorizado antes de abrir conexão. O runner executa essas quatro verificações negativas antes de migrations; a rejeição de `condoos` foi demonstrada antes de qualquer escrita.
- O runner lê `DATABASE_URL` do ambiente ou do `.env.e2e.local` ignorado e nunca reescreve a URL recebida. `.env.local` fornece somente `SESSION_SECRET`. A identidade viva é verificada antes de migrar, e nenhuma URL, senha, sessão, token ou chave é impressa. As migrations Drizzle já versionadas foram aplicadas; `db:push` e `db:push-force` não foram usados.
- Cada execução cria dois tenants, administradores A/B, usuário limitado A, roles e dados mínimos para unidades, residents, charges/payments, suppliers/services/contracts, marketplace e API Keys. O nome e as identidades dos fixtures são temporários e únicos. O teardown apaga os tenants por cascade; nenhuma chamada a seed foi feita.

## Cobertura automatizada

- Sessão: login válido/inválido, cookie HttpOnly com `SameSite=Lax` e `Path=/api`, ausência de JWT no JSON, `/auth/me`, logout, sessão ausente e cookie inválido.
- CSRF/origem: mutação sem token e token inválido recebem 403; token válido permite a mutação; origem não permitida é bloqueada. `condominiumId` adulterado no body e query não muda o tenant autenticado.
- RBAC: falta de sessão 401, usuário limitado autorizado e negado em grupos diferentes, administrador `*`, escalada por atribuição de role bloqueada, conta desativada e role removida/inválida negadas.
- Isolamento A→B e B→A: GET, UPDATE e DELETE de unidade cross-tenant são negados; listas de users, roles, units, residents, charges, payments, suppliers, services, contracts, API Keys e marketplace mostram somente o tenant autenticado. FK cross-tenant de unidade para charge é bloqueada. As linhas pertencentes ao tenant dono permanecem intactas.
- API Keys: criação via JWT/RBAC, segredo retornado na criação, segredo/hash ausentes na listagem, scope válido e scope ausente, chave inválida, hash usado como credencial, revogação imediata, isolamento entre tenants, API Key sem administração de chaves e credenciais simultâneas rejeitadas.
